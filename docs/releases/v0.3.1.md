# v0.3.1

導入・起動・状態確認の操作を簡略化し、実行条件と各生成の所要時間を追える保存形式に更新しました。

- 任意のself-managed-llama補助：llama/に配布物、llm/にGGUFを配置。確認・設定生成・起動・停止をtools/で提供。
- SELF_MANAGED_LLAMA、LOCAL_GGUF_PATH等を追加。既存のllama.cppサーバーへの接続も維持。
- enqueue時にセッションを即時作成し、必要ならサーバーとバックグラウンドworkerを自動起動。
- statusで状態・処理段階・完了ターン数・更新時刻を表示。
- 実モデルテストは10秒ごとに状態表示。既定の待機上限1時間、超過は完了未確認としてコード2で終了。処理は止めない。
- APIリクエストの既定タイムアウトも3600秒へ変更。テスト全体の待機上限とは別設定。
- 保存形式schema_version=1.0。各turnをindex/character/coordinatorへ整理し、output/metrics、初期化・締めの記録、実効設定、モデル情報等を追加。
- セッション名をUTC日時・ミリ秒・ランダムIDへ変更。

## v0.3.0からの移行

1. 旧フォアグラウンドworkerをCtrl+Cで停止してから更新してください。
2. 既存セッションはそのまま保持してください。新形式に自動変換しません。会話を読むツールは新旧形式を区別する必要があります。
3. 既存サーバーを使う場合、.envにSELF_MANAGED_LLAMA=falseを指定します。LOCAL_*は不要です。toolsのenqueue/testは.envを必須としますが、環境変数で上書き可能です。
4. self-managed-llamaを使う場合はREADMEの配置・確認手順に従ってください。空のLOCAL_GGUF_PATHはユーザーが設定できます。
5. `python3 tools/enqueue.py samples/input.json` が新しい基本操作です。`chatwell enqueue --input ...` も自動起動するようになり、表示するパスは内部依頼JSONからセッションJSONに変わりました。
6. 自動起動workerを止めるにはtools/stop-worker.py。現在の依頼が終了後に停止するため、セッションとログで完了を確認してください。SELF_MANAGED_LLAMAの停止は別コマンドです。

既存の待機依頼はworkerが新しいセッション形式で処理します。新規依頼は登録時点でセッションを作ります。旧ファイル名や旧セッションは変更しません。既存の旧依頼JSONにsession_pathがない場合は処理開始時に新規作成します。

v0.3.1の保存形式変更とenqueueの動作変更を含むため、下流で旧形式や登録のみの挙動に依存している場合は移行が必要です。今回合意したバージョンをv0.3.1としています。

## 検証範囲

Linux x86_64/Python 3.12で既存の会話処理と新しい保存形式、実効設定、失敗時メトリクス、待機上限、バックグラウンドworkerを検証。self-managed-llamaのプロセス起動・認証・停止・モデル識別情報はHTTPサーバーの代用品で検証します。実GGUFと各OS向け配布バイナリの検証は別途必要です。Windows/macOSはCI対象ですが、クラウド上で実行したとは扱いません。

samples/output.jsonは実モデル実行後に追加する想定です。添付のv0.3.0出力をv0.3.1の実行結果として扱いません。
